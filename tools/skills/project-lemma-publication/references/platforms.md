Before porting, read the current [toolchain minimum](https://github.com/PalomarRegistry/PalomarSubmission/blob/main/toolchains.json). Audit the proven imports separately from the deliberate Challenge holes.

Run the full reusable submission workflow on the exact public SHA. Pin the workflow and its pipeline input to the same full PalomarSubmission commit. Use the standard public runner profile, a twelve-character lowercase alphanumeric request ID, repository-relative paths and the truthful authorization relationship. Inspect the mechanical report for a pass, including the kernels and resources it actually used. After a pass, show the user the repository, full commit, configuration path and relationship and obtain their agreement under the [agent intake protocol](https://submit.palomar-registry.org/llms.txt). Only then start the short-lived tag and secret-gist challenge. Keep the token private. After the review, show it to the user and explain permanent registration before requesting that separate instruction.

## Archiving and database updates

For an eligible, authorized Zenodo deposit, search title, creator and related release/version across public records and account drafts first. Upload the already verified problem-specific release assets and SHA256SUMS.txt. Use the final abstract, date, version, real human creators, licensing by component, release relation and explicit AI description. Verify the registered version DOI and public files before updating CFF, README and release notes. Preserve the old artifacts.

For databases, query the live supported parameter range, definitions and direction of the bound. Distinguish a universal obstruction from an attaining construction. Record date, scope, pagination, exceptions, old lower/current upper, new lower/exact, prior witness and proof links. If bulk access is unavailable, use ordinary public filters within site limits. Report any remaining coverage gap. For 001 the browser tables worked when raw HTTP returned 403. The live comparison checked 1,955 entries and identified 39 proposed changes. One notification was sent. Further contact requires a new reason and authorization. Maintain acceptance and table changes as separate evidence.

Compare the exact sent message, recipient and attachments before any retry. With appropriate authorization send a single concise report giving the theorem, affected records, versioned proof and artifact, formal status, AI provenance and human peer-review status. A permanent GitHub release is sufficient when a DOI is unavailable. Do not request extensive unpaid review.
