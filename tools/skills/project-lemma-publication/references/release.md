# GitHub, recovery and replay

Run repo commands from the canonical checkout. Check origin, current branch, local changes, upstream main and the public target before any push. Use one publishing session per problem, version and destination. Honor the current request. Earlier authorization or a stored receipt is evidence of a past action, not ongoing permission for new ones.

1. **Reconcile.** Locate the numbered investigation and its `PUBLICATION.md`, tag, release notes, checksums and workflow. Inspect public records at the version and current service status. Match existing external IDs, scope and author, including drafts, already-sent mail and pending tickets. When using another checkout or resuming a handoff, fetch the latest record and ask the owning session about unresolved intent. Missing records are unknown, not evidence of absence.
2. **Prepare.** Finish the research checks. Update problem-specific CFF, README, change history and the live project index from the accurate title, summary and status. Run `python <skill>/scripts/problem.py --repo <checkout> index <NNN-slug> --title "<title>" --summary "<result>" --status "<evidence-backed status>"`. It updates the root and directory indexes. Review any existing featured narrative for stale claims. On recovery from an interrupted index update, repeat the same inputs. A leftover `.publication-index.lock` requires checking for a live writer before removing that one empty lock.
3. **Audit the candidate.** Adapt the existing problem-specific workflow in `.github/workflows/`; pin the Lean toolchain, libraries and actions, use path filters and free public runners. Separate certificate replay, manuscript compilation and formal contracts. Validate CFF against its declared schema. Rehearse in a clean temporary checkout with documented dependencies. Commit the audited candidate locally. Run `python tools/package_release.py <fresh-output-directory> --rev <commit> --problem <NNN-slug> --tag <slug-vX.Y.Z>`. Use a new directory for a different version. The script reads Git blobs from the selected commit, the problem's CFF version and its paper/paper.pdf, preserves shared files and excludes other investigations' problem trees. Extract and rebuild, verify source correspondence and checksums. For 001 the historical tag is `mills-14-v1.0.0`.
4. **Publish when authorized.** Push the candidate normally. Require a successful run of the *named* problem workflow on that exact SHA with all applicable jobs passed. Inspect actual job results, repair and repeat failed checks. Prepare release notes with precise results, disclosure, archival scope and peer-review status. Check both authenticated draft releases and tag refs. Create or resume one draft at that SHA, attach the exact PDF, ZIP and SHA256SUMS.txt, compare the asset sizes/digests, then publish. A conflicting tag or different bytes on a published release calls for an explicitly versioned correction. Never force-push, replace a published asset or move a published tag.
5. **Verify.** Fetch the tag locally, then use the anonymous read-only checker below. Inspect separately the formal report, mathematical checks and current publication record. The checker verifies GitHub's asset digests, manifest, byte contents of the tagged source tree and PDF, and the most recent matching branch/manual CI run. It requires the expected jobs by name. Network failure or missing evidence means the check is incomplete. Preserve its JSON output or the associated public links and hashes in the publication record.

```sh
python <skill>/scripts/audit_release.py --repo <checkout> --problem 001-mills-number-14 --tag mills-14-v1.0.0 --workflow mills-14.yml --require-job "Clean Lean build and theorem audits" --require-job "Certificates and supplementary results" --require-job "Compile manuscript and bibliography"
```

**Tools.** Prefer an authenticated connector or GitHub CLI. Standard CLI equivalents include `gh auth status`, `gh run list --workflow FILE --commit SHA`, `gh run view ID`, `gh release list`, `gh release create TAG --draft --target SHA --notes-file NOTES`, `gh release upload TAG FILES`, and `gh release edit TAG --draft=false`. Supply actual paths and verify owner before mutation. If the CLI is absent, use ordinary Git plus the official GitHub REST release endpoints with existing host-authorized authentication. Keep credentials out of arguments, output, repository and skill. For archives or alternate layouts outside this packager's contract, compare the published assets directly to their documented tagged manifests and record that method.

**Action receipts.** The durable human-facing ledger is `PUBLICATION.md`; add one immutable action-key record per new remote operation that could be duplicated. Choose a key from problem version, destination and purpose, stable across retries. Before a send, submission or release creation, inspect the external system even when this is the first local run:

```sh
python <skill>/scripts/receipts.py <problem-dir> inspect v1.0.0.registry.deposit
python <skill>/scripts/receipts.py <problem-dir> begin v1.0.0.registry.deposit --evidence "Authorized destination and version; existing records checked"
# Only the session that newly reserved this action may perform it.
python <skill>/scripts/receipts.py <problem-dir> finish v1.0.0.registry.deposit --outcome confirmed --evidence "<verified submission or sent receipt>"
```

Use an exclusive writer and share the reservation through the project's record before any parallel handoff. The helper prevents duplicate reservation within a checkout; it cannot lock a remote service or a different clone. If the call times out, leave the intent unresolved and query the service's drafts, published objects, support queue or sent folder. Resume an identifiable draft by ID. Only retry the same reserved action after positive evidence that the first request did not take effect. If ambiguous, stop that action. If already completed, record the evidence and skip it. Record rejection or withdrawal accurately. Distinguish receipt of a message from acceptance of a result. Keep personal addresses and private ticket links in private evidence.

**Maintenance.** Record one short lesson for each novel failure and its verified fix. Change the portable skill in this repository, update its changelog, validate and test it on disposable data, then reinstall/synchronize that revision. Compare installed file hashes. Use the official installer for a new install. For a refresh, preserve local edits or back up a differing installed copy before replacing only this skill. No automatic background publication or platform polling is installed.
